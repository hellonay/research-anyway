# 접근 권한 (Access Control)

## Decisions

- 이 앱은 계정별 로그인을 두지 않는다. 대신 배포 전체를 공유 비밀번호 하나로 잠근다. 비밀번호를 아는 사람은 누구나 전체 내용을 열람하고, Day와 일정 항목을 추가·삭제할 수 있다.
- 비밀번호는 `SITE_PASSWORD` 환경 변수로 설정하고, `proxy.ts`가 모든 요청에서 세션 쿠키(`lib/auth/session.ts`)를 검사해 없거나 틀리면 `/login`으로 돌려보낸다.

## Boundaries

- 뷰어와 편집자 구분, 사용자별 계정, 초대 코드, 트립별 개별 비밀번호는 이 결정의 범위 밖이다.
- `app/actions.ts`의 서버 액션 각각에는 별도의 세션 검사를 추가하지 않았다. `/`, `/info`, `/photos` 세 페이지가 모두 Proxy matcher에 걸려 있어 지금은 안전하지만, matcher가 바뀌어 이 페이지들이 제외되면 액션 보호도 함께 사라진다(Next.js 인증 가이드가 명시한 위험).
- 여러 여행(트립)을 다루게 되어도 트립별 접근 제한을 두지 않는 것이 기본값이다.

## Why

친구들끼리 여행 준비 정보를 빠르게 공유하는 것이 목적이고, 계정 기반 인증(사용자 테이블, 회원가입, 비밀번호 해싱)을 구현하면 "한 번에 구현하고 실제 동작으로 검증"할 수 있는 범위를 벗어난다. 반면 배포 URL이 검색엔진이나 우연한 접근으로 노출될 경우 개인정보가 담긴 일정이 그대로 보이는 문제가 있어, 계정 없이도 낯선 사람의 우연한 접근만은 막을 수 있는 공유 비밀번호 하나를 추가했다.

## Reconsider when

- 여행 페이지가 불특정 다수에게 공개되어 악의적 삭제가 발생하거나, 여러 그룹이 같은 배포를 공유해 데이터가 섞이는 문제가 생기면 재검토한다.
- 누가 수정했는지 구분해야 하는 요구가 생기면 계정 기반 인증을 재검토한다.

## Still-rejected alternatives

- 로그인 기반 멤버 인증(계정별 이메일/비밀번호 또는 OAuth) — 사용자 테이블·세션 관리 등 구현 범위가 커져 보류; 여러 그룹이 동시에 쓰는 서비스로 확장할 때 재검토.
- "여행 종료일 N일 후 자동 만료" — 별개 요청으로 논의했으나 이번 작업 범위에서 보류.
